# Attachment storage

Orvyn defaults to S3 when `ORVYN_STORAGE_DRIVER` is absent. Existing S3 object keys, authentication, private downloads and retention stay compatible. API and worker must use the same driver and credentials or shared directory.

For native filesystem storage set `ORVYN_STORAGE_DRIVER=local` and `ORVYN_STORAGE_LOCAL_PATH=/data/attachments`. The directory must be private to trusted Orvyn processes, writable by their common UID (1000 in the production images), and mounted into both API and worker. The driver creates a private `orvyn-objects/` namespace, hashes object keys with SHA-256 into shard directories, creates files with mode 0600, and commits writes with fsync and atomic rename. Readers receive streams; uploads retain the existing configurable 1 byte–100 MiB limit. File names never become filesystem paths. Symbolic links and traversal keys are rejected. Do not expose the directory through a static web server.

API operations, database-template file copies, public attachment grants, and Markdown bundle exports use the same typed backend. Access checks remain in the application. Pending/failed uploads and expired trash are removed by the worker using existing database retention rules; abandoned staging files older than an hour are cleaned in bounded batches. Never run external cleanup against active uploads. A mounted directory with untrusted concurrent writers is unsupported.

For S3, configure `S3_ENDPOINT`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_REGION` (default `us-east-1`) and `S3_FORCE_PATH_STYLE`. Provision a private bucket and suitable credentials. `node scripts/storage-init.mjs` initializes local-development S3 and checks privacy and integrity. The compiled `node dist/commands/storage-init.js` command is used by the Helm chart only for its own internal SeaweedFS bucket; external buckets are never created automatically.

Back up the database, attachment objects and persistent encryption key together. Local files are opaque and content metadata lives in PostgreSQL. Keep file ownership and permissions when restoring. Stop API and worker while taking a consistent filesystem/database snapshot, or use coordinated storage and PostgreSQL snapshots. For S3 preserve exact object keys, bytes and bucket policy; provider versioning is recommended.

Changing the driver or path does **not** migrate data. For a controlled migration, put the instance into maintenance, stop all API/worker writers, take and verify backups, and copy every `files.object_key` still referenced by the database (including pending/trash/publication/template references) through the source backend's `get()` and destination backend's `put()`. Verify object sizes and SHA-256 digests, retain the database's original keys, then switch API and worker together and test authenticated downloads, templates, exports and cleanup. Keep the original store and backups until rollback is no longer needed. There is no automatic migration command; do not rename hashed local files into S3 keys. Returning to the previous driver after new writes requires another verified copy.

Helm supports an existing attachment PVC, ReadWriteMany storage for multiple pods across nodes, or one API and one worker colocated on ReadWriteOnce storage. These modes do not by themselves establish high availability. Ephemeral filesystem mode shares an `emptyDir` between API and a worker sidecar and loses attachments when that pod is replaced; use it only for disposable tests.

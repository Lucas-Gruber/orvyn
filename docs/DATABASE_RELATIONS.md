# Database relations

Relation properties link records to a configured database in any currently accessible space, including the current database. Creating a relation requires editor access to the source and at least reader access to the target database; it does not grant access to the target space. Database selection reuses the indexed workspace search in database/title-only mode, with space filters, keyboard selection and cursor pagination. A property can contain multiple records. The picker searches current readable targets, supports keyboard selection and opens records through permanent page links. Renames and access changes update open tables across collaboration replicas.

The server validates the target database when creating a property and validates every explicitly submitted record ID when saving values. Requests may select up to 50 currently readable records at a time. Previously stored inaccessible links remain stored, but are excluded from values, labels, filters and exports. Editing the visible selection preserves those unseen links. Explicitly submitting an inaccessible existing ID or an unknown ID produces the same validation error. The underlying stored list can therefore exceed 50 links after access changes and subsequent visible edits.

The transactional `record_relations` projection holds structural references, not permission snapshots. Queries resolve current source and target access. Relation filters (`contains`, equality and empty checks), saved views and CSV/JSON exports use that filtered projection. Scoped views return target metadata only for their visible relation columns. List sorting is unsupported. The picker does not disclose hidden counts or titles.

CSV import can map to an existing configured Relation property using UUID arrays (JSON or semicolon-separated IDs). Both preview and commit validate current readable targets; a changed permission at confirmation rejects the complete import. Creating a new relation directly from an unconfigured CSV column is unsupported.

Live subscriptions watch only currently readable related targets for the visible relation columns. A permission change removes a formerly readable target once; later activity on an inaccessible target sends no relation invalidation. A fingerprint of the HTTP snapshot is compared during watch registration so changes between loading and subscribing trigger a refresh. Fingerprints contain no content and do not authorize access; subscription records and targets are checked independently.

Relations can be one-way or created with a matching property in the related database. [RECIPROCAL_RELATIONS.md](RECIPROCAL_RELATIONS.md) describes two-way setup, atomic writes, permissions, deletion, templates and the 50-link stored limit. Direct rollups, formulas and database/record templates support cross-space targets with current independent target checks. Multi-hop rollups remain unfinished. There is no public sharing of relation targets.

Migration 36 removes the old same-space restriction from structural relation projection and actor-filtered reads, backfilling edges without rewriting page/record revisions. A target’s inherited page/database permissions and space membership still filter every read. Source-side ownership alone does not authorize a target. Revocation hides values, labels, calculations, picker entries, template defaults and exports; subsequent activity on the inaccessible target sends no source invalidation. Stored hidden references survive edits to the visible selection, and become visible again only if access returns. Database template application fails if its configured external target is no longer accessible; record template application omits newly inaccessible defaults. Cross-space template transfer itself remains separate work.

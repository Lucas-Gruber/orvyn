# Database rollups

Rollup properties calculate a read-only number from directly related records in any currently accessible space. Choose an existing Relation property, then Count records, Sum, Average, Minimum, Maximum, Count nonempty values or Count unique values. All calculations other than record count also select a compatible field in the target database. Click a rollup column heading to edit its name/configuration with optimistic schema-version checks.

Numeric aggregates accept Number fields, local numeric Formula fields and numeric Rollup fields. A rollup over another rollup follows at most two relation steps: for example Areas → Projects → Tasks, summing each project's task hours. Aggregations compose over readable intermediate records; a task linked to two projects contributes to both project totals. Nonempty/unique counts accept scalar fields and local scalar formulas. Target formulas may use local record fields, metadata and other local formulas; dependencies on Files, Relations or Rollups are excluded. Cycles and paths longer than two steps are rejected during configuration; a later target-schema change that creates an unsupported path makes the existing calculation unavailable. Longer chains, multi-hop formula expressions, original-value arrays and date extrema remain unimplemented. A source formula may use the numeric result of a rollup, for example `prop("Total hours") * 80`.

Every query recalculates from the current actor's readable relation projection. Private targets do not contribute to counts, sums, filters or exports. A readable database with no matching targets yields zero for counts/sum and null for average/minimum/maximum. Empty values are ignored by value counts and numeric aggregates; zero and false remain nonempty. A missing/inaccessible target database, removed field or incompatible changed target formula yields null. Numeric aggregates use numeric intermediates and return finite double-precision results; overflow produces null.

The server authorizes target schema lookup independently of source-space ownership while holding the source write lock for configuration. A source editor needs current reader access to each configured target database, including when targets belong to other spaces. Related schemas are held in a weak sidecar map and are never serialized in source metadata or exports. Queries compile a fixed aggregation allowlist and bind all property/database IDs. Calculations happen before server-side filters, sorts and pagination. Query/single-record reads and exports use repeatable-read snapshots so schema catalogs, calculated values and dependency fingerprints remain consistent during concurrent changes. Record mutation responses, CSV and JSON exports use the same calculation semantics. Rollup results cannot be patched or imported; CSV mapping skips matching computed columns.

Live subscriptions include a rollup's Relation dependency even when that Relation column is hidden. Direct and second-step record edits, schema changes and access revocation refresh loaded source rows across replicas. Leaf schema markers remain present when intermediate records have no linked leaves, so deleting a leaf field still clears the calculation. Later activity on already inaccessible targets sends no relation invalidation. The HTTP snapshot fingerprint includes actor-filtered second-step dependencies, closing the race between loading a result and registering its live watch. Migration 38 adds dependency functions without rewriting records or document versions.

For dense results exceeding 10,000 readable dependency path instances (including reachable leaf-schema markers), the web client refreshes permission-checked values every five seconds. The watch acknowledges this mode and skips repeated deep dependency scans; older clients receive a fixed five-second refresh signal. The mode is derived from authorized paths only, and pagination lookahead rows do not affect the visible result's budget. This bounds ongoing watch work, not total query cost; production graph/load testing remains outstanding. As with relations/formulas, target-only changes to source records outside the currently loaded result/page can require refreshing to include newly matching records.

Dependency inspection authorizes each distinct reachable leaf once per source record and shares the output scan for its digest and budget, retaining at most 10,001 output nodes. Candidate discovery and the numeric calculation still depend on the actual graph size. Numeric aggregates join authorized relation edges directly instead of repeatedly expanding a JSON relation projection. Interactive snapshot reads and dependency functions disable PostgreSQL JIT locally to avoid compilation pauses as the planner's estimates grow; other transactions retain the database's normal setting.

Validation: `tests/database-rollups.test.mjs` covers direct aggregates and the build/edit/reload/reader flow. `tests/multi-hop-rollups.test.mjs` covers composed aggregates, independent permissions, filters/sorts/formulas/exports, cycle/depth checks, later schema changes, cross-replica leaf refresh, private activity silence, stale watch registration, a gated concurrent catalog/value snapshot, dense fallback and legacy watches, and desktop/mobile Chromium configuration plus dense-result refresh.

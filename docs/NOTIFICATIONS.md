# Comment mentions and inbox

In a new comment, reply or author edit, type `@` and choose a person from the menu. Arrow keys/Enter select; Escape dismisses. The page-scoped directory includes only current space members/owner who can read that page. Up to 20 people can be selected per message. The composer keeps ordinary readable `@email` text and a separate set of chosen user IDs; typing an email without selecting a person does not send a notification. This slice covers discussions. Inline people nodes in the rich-document editor follow separately.

The server validates each selected identity, current page access and the corresponding label in the body under the space write lock. Unknown/ineligible recipients receive the same generic input error. Self-mentions are kept on the comment without notifying the author. Repeated references to one person and a retried submission produce one notification. New mentions on an author edit notify only newly added recipients; retaining an existing mention leaves its read state alone. Removing a mention or deleting the message removes its mention notifications. A former/inaccessible recipient must be removed from the selected mention set before reusing it in an edit; the text remains ordinary comment text.

A reply also notifies prior discussion authors who still belong to the space and can currently read the page. Merely being mentioned does not subscribe someone to later replies. One recipient/message pair produces at most one item, with an explicit mention taking priority over the generic reply event. There is no email dispatch or subscription preferences yet.

Open **Inbox** in the sidebar. Items support unread/all filters, individual read/unread toggles, mark-all-read, pagination and navigation to the current discussion. Opening checks current authorization again. Navigation pauses and flushes document editing just like ordinary page navigation. New-comment/reply drafts retain their chosen identities in memory per page/thread; account changes clear this cache.

Migration 25 adds comment mention identities and a per-recipient notification table. Notifications store source IDs, actor ID, kind, timestamps and read state; they do not store page titles, message excerpts or quotations. List/open/read/count operations join the current page/thread/message and re-evaluate inherited permissions, including ancestor restrictions, trash and lost membership. Source reads hold shared space locks while permission/mutation endpoints hold exclusive locks. Missing/inaccessible IDs share not-found responses. Deleted source messages/threads disappear from feeds. Actor email is withheld after leaving the source space. Mark-all-read touches only currently accessible items.

The list uses creation order with caller-scoped UUID cursors (default 20, max 100). The badge and first list page refresh every 15 seconds while the browser is visible; the refresh button updates immediately. Loading older pages suspends automatic list replacement until refresh. Inbox state is in memory and remounts on account changes. Push delivery, offline notification storage, email, desktop notifications, mute/follow preferences and a user-visible activity history remain separate work.

API tests verify recipient validation, retries, editing/removal, self-mentions, mention/reply deduplication, read state, current titles/excerpts, privacy of counts/read actions, scoped pagination, membership/restriction/trash/deleted-source boundaries and origin enforcement. Chromium covers the chooser, actual posting, inbox navigation, read controls across reload, participant replies and mobile width.
